## 2. The project
A **visual effects library** for the **Pixelfork AI Engine**, which generates hyper-casual and casual 2D/3D mobile web games.

The point of this library is that **an AI building a game should never spend time or tokens designing particle effects**. It writes `VFX.play('hit.impact', {x, y})` and the effect is already there, already tuned, already the right size. The library is the companion to the **Super Casual UI Kit** (`../Mobile Game UI Library`) and the **SFX Library** (`../SFX Library`), and follows the same conventions as both.

The owner is **non-technical**: explain results in short, plain language. **Work in small steps, one task at a time.** **End every reply with exactly one "Next task: …" line.**

## 4. How to add an effect (follow exactly)
1. Copy the closest file in `packs/casual/effects/`, rename it `category.thing.js`, set `name`, `category`, `whenToUse` (one plain sentence a game-building AI can match), `duration`, `loop`, `tint` (default hex, `null` = tint replaces the whole palette, or omit for untintable), `tags`.
2. Write `build(c)` with `c.sys({...})`. Units are **design pixels at size 1** on a ~400px-wide phone. Use `c.color('#hex')` for the main colour so `tint` works.
3. Import it in `packs/casual/index.js`.
4. `node tools/build.mjs` — validates names, bundles, writes the registry and the AI-guide table.
5. Look at it: `node tools/serve.mjs 8767` → `tools/preview.html`. Use **Slow motion**. Check it at size 0.5 and 2, and with a tint.
6. If it is a UI-kit moment, wire it in `attach()` in `src/vfx.js` and check it in `demo/game.html`.
7. Update **`STATUS.md`** and **`CHANGELOG.md`** (see §7).

**Comments in effect files go on their own line, above the code.** A `//` in the middle of a line comments out every option after it on that line, silently. It happened twice (confetti lost its colours, rain its streaks). The build now refuses such lines.

## 5. Design rules (the owner approved these; never break them)
- **Style:** modern mobile casual — chunky, bright, glossy, cartoon. Bold shapes, saturated colours, short and punchy. Not realistic, not gritty, not cinematic. Same family as the UI kit.
- **Every effect must support `tint`** where a colour makes sense, via `c.color(default)`. One `pickup.sparkle` must work gold, blue or pink without a new entry.
- **Short.** Hits and pickups under 0.7s, rewards under 1.5s, only confetti goes past 3s. Loops must look right for minutes.
- **One call, no setup.** A game never creates a canvas, a renderer or a loop. The overlay makes itself on the first `play`.
- **Sizes are design pixels.** A hit is ~100px wide, an explosion ~150px, a level-up ~250px at size 1. `size` scales everything; `VFX.size` scales every effect at once.
- **Nothing loads.** Textures are drawn in code (`src/textures.js`). If an effect truly needs a picture, that is a design discussion with the owner first.
- **Names are a contract.** `category.thing` in lower case; the category is the first part. Once a name ships, renaming it breaks every game that uses it — add `aliases: ['old.name']` instead.
- **Never let a missing effect throw.** Unknown names warn once and return an inert handle.
- **Loops must stop cleanly.** `handle.stop()` lets particles finish; `kill()` is instant. Test both.
- **Performance budget:** 120 fps on a laptop with 5 effects at once; no more than ~300 live particles per effect. Materials are shared through `helpers.makeMaterialCache` so every texture+blend pair is one draw call — do not create materials in effects.

## 6. Three quirks of three.quarks we work around (do not undo)
1. **Stretched billboards need camera depth.** Their width is `cross(viewPosition, velocity)`; with the ortho camera at z=0 it is zero and sparks vanish. The overlay camera sits at `z = 1000`.
2. **Forces act in emitter-local space.** A cone turned to shoot "up" turns gravity too. `helpers.sys()` counter-rotates every `ApplyForce` direction on rotated emitters (unless `world: true`).
3. **Looping systems keep firing bursts after `endEmit()`.** `handle.stop()` sets `looping = false` first.
4. **Textures must be white-only data textures** (`src/textures.js → make()`), never `CanvasTexture`. Chrome dithers canvas gradients and stores premultiplied pixels; uploaded as a canvas texture that becomes random per-channel colour noise at faint alpha, and additive blending stacks it into visible red/green grain. Keeping only the alpha from the canvas and forcing RGB to 255 removed it (confirmed by the owner on screen; my pixel readbacks could not show it, so do not "verify" this one with readPixels).
5. **The overlay canvas uses `premultipliedAlpha: true`** (three.js default). With it off, the compositor showed the same grain.
6. **Rect emitters push particles sideways, not forward.** `RectangleEmitter` spawns on the rectangle's edge with velocity pointing away from its centre, so a flat rect line (`h: 0`) with `speed` sends everything along the edge. For anything falling or rising from a screen edge use `speed: 0` and drive it with `c.gravity` / `c.force` + `c.limitSpeed` (see `env.rain`, `env.snow`).
14. **Generated games play effects at `object.position`**, the centre of a solid mesh. `autoPull()` moves the camera-facing part in front of that model. When testing 3D effects, test them ON a model's centre (see `demo/three-cdn.html`), not only on surfaces and in open air, or you will never see this class of bug.
13. **One three.js per page.** Never tell a 3D game to load `dist/vfx.js` beside its own three.js: three.quarks' shader chunks live in the copy it imported, so with two copies the particle shaders do not compile. 3D = `dist/vfx.module.js` + import map. The 3D player is the living test of that path; keep it on the import map.
12. **Trails.** `WidthOverLength` sets the ribbon width to the curve's RAW value in world units (it ignores `size`), and its curve goes newest point (t=0) → oldest (t=1). The trail shader's u runs along the ribbon with u=0 at the OLDEST point. `c.ribbon()` and the `ribbon` texture are built around both facts; read its comment before changing either.
11. **Draw order in 3D.** Particles do not write depth, so any transparent game object drawn after them paints over them. In scene mode all systems get `renderOrder + 1000`. Keep effect `order` values small (they are relative) and never give a game's transparent meshes a render order above that.
9. **Colour spaces.** Sprite and trail shaders in three.quarks write colour RAW (no output conversion); only the lit mesh shader (`particle_physics_frag`) converts linear→sRGB. So hex colours are used as written everywhere, and `colorGen(c, true)` feeds linear values only to lit debris. Do not "fix" sprite colours with a linear conversion — that was tried and made smoke black.
10. **One effect file, two worlds.** 3D upgrades are wrappers that return their input unchanged in 2D: `c.vol`, `c.chunks`, `c.flat`, `c.ground`, `c.spray`, `c.env3d` (and `c.heading()` + `c.wind()` for 3D-only wind); `c.ribbon` returns null in 2D (the runtime filters nulls). Systems they mark `in3d` go in the handle's world-aligned `group`; everything else goes in the camera-facing `face` child.
8. **3D facing.** In a scene, `faceCamera()` turns each effect's flat design plane to the camera and re-aims every `ApplyForce` from its recorded design direction (`b._design`, set in `helpers.sys`). If you add a new force-like behaviour, record its design direction the same way or it will tilt with the camera.
15. **Mesh particles ignore `texture.repeat`** (the unlit mesh path samples `map` with the raw `vUv`), and a UV sphere pinches any texture at its pole. The hex dome is therefore built from real tiles by a custom emitter shape (`helpers.TilesEmitter`): `EmitterShape.initialize()` runs LAST in three.quarks' `spawn()`, so a shape may override position, rotation, size, velocity and life per particle.
7. **Stretched particles map their texture along the motion.** Use round textures (`glow`, `disc`) with `stretch`; the `line` texture turns into an invisible sliver (it is for un-stretched use only).
